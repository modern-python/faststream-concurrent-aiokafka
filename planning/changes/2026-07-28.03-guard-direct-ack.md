# Change: Refuse direct `msg.ack()` / `nack()` / `reject()` on the concurrent path

**Lane:** full — public-facing behaviour change (a new runtime error),
cross-cutting, and the test design has a load-bearing negative case.

## Summary

On the `_Dispatch` path, `consume_scope` shadows `ack`, `nack` and `reject` on
the `KafkaAckableMessage` instance with synchronous guards that raise
`RuntimeError`. Handlers and inner middleware both see them, because both
resolve the message from the same object.

## Motivation

Offsets on this path belong to `KafkaBatchCommitter`. Reaching around it is
silent data loss today, and nothing stops it:

- `KafkaAckableMessage.ack()` issues a bare `consumer.commit()` with no offsets
  (`faststream/kafka/message.py`). That commits the consumer's **current fetch
  position** — past every in-flight task on every assigned partition. Those
  messages are never redelivered and never processed. No error, no log.
- `reject()` is literally `await self.ack()` for Kafka, so it carries the same
  hazard under a name that sounds like the opposite.
- `nack()` issues `consumer.seek(partition, offset)`, rewinding the partition
  underneath tasks already processing it — duplicate delivery, and a hot loop if
  a middleware does it per message.

[`2026-07-28.02`](2026-07-28.02-absorb-control-signals.md) handled the
*exception* form of these requests (`AckMessage`, `NackMessage`, …). This is the
direct-method-call form, which that change explicitly left open and which
[`deferred.md`](../deferred.md) has tracked since. Since 0.6.4 the README tells
users not to do it; nothing enforces it.

## Design

`StreamMessage` is a plain class with `__dict__`, so `setattr(kafka_message,
"ack", guard)` shadows the class method for that one instance. Handlers resolve
`KafkaMessage` via `Context("message")` (`faststream/kafka/annotations.py`) —
the same object `consume_scope` holds — so one mutation covers handlers and
inner middleware without a proxy, wrapper threading, or contextvar work.

That identity is the crux, and it holds by construction: `process_message` binds
one `message` variable, enters `context.scope("message", message)` with it, and
passes the *same* object into `h.call(message=message, …)`, which threads it
through every `consume_scope`. So `consume_scope`'s `msg` parameter, the
`kafka_message` read from context, and whatever a handler receives via
`Context("message")` are all one object. The guards go on the `kafka_message`
the middleware already holds.

All three are shadowed, not just `ack`: `reject()` delegates to `self.ack()`, so
guarding only `ack` would report the wrong method name to a `reject()` caller.

**The guards are synchronous.** A sync function that raises fires while
*evaluating* `msg.ack()`, before the `await`. An async guard would only fire if
awaited, so a bare unawaited `msg.ack()` would degrade to a `RuntimeWarning`
instead of an error.

```python
def _refuse_direct_ack(method_name: str, *_args: object, **_kwargs: object) -> typing.Never:
    raise RuntimeError(_DIRECT_ACK_REASONS[method_name])
```

### Where it installs, and why that is load-bearing

Only in the `_Dispatch` branch of the existing `_classify` match:

| route | guard | why |
|---|---|---|
| `_Dispatch` (`AckPolicy.MANUAL`) | **yes** | this library owns the offsets here |
| `_PassThrough` (FakeConsumer) | no | `TestKafkaBroker` tests that ack must keep working |
| `_PassThrough` (`AckPolicy.ACK_FIRST`) | no | offsets belong to aiokafka's `enable_auto_commit` |
| `_Refuse` (every other ack policy) | no | nothing is dispatched — see below |
| `_Skip` | no | nothing is dispatched |

The guard is safe precisely because it is scoped to the path where FastStream
has delegated acknowledgement to us — under `AckPolicy.MANUAL` no
`AcknowledgementMiddleware` is built at all, and a grep of the installed package
confirms the only other callers of these methods are `KafkaAckableMessage`'s own
internals.

### Routing change: refuse every ack policy except MANUAL and ACK_FIRST

Writing the guard exposed a pre-existing hole in `_classify`. The old code
treated `committed is not None` as "this is an auto-ack subscriber, pass it
through", on the assumption that the complement (`committed is None`) meant
`AckPolicy.MANUAL`. It does not. In FastStream:

- `faststream/kafka/subscriber/usecase.py` picks the non-ackable `KafkaMessage`
  (which starts `committed=AckStatus.ACKED`) **only** for `ACK_FIRST`. `ACK`,
  `REJECT_ON_ERROR` and `NACK_ON_ERROR` all get `KafkaAckableMessage` with
  `committed=None`, exactly like `MANUAL`.
- `faststream/kafka/subscriber/config.py` disables the auto-ack middleware only
  for `{MANUAL, ACK_FIRST}`, so those same three policies **do** build
  FastStream's `AcknowledgementMiddleware`.

So three policies were reaching `_Dispatch`: fired as a background task *and*
acked by FastStream the instant `consume_scope` returned — a bare
`consumer.commit()` ahead of every in-flight task on every assigned partition.
Silent message loss, unrelated to the guard, present since the routing was
written.

The ruling is to **refuse them**, not to pass them through: passing through
would silently drop concurrency for a subscriber the user asked to process
concurrently, and the configuration is wrong either way. `_classify` therefore
takes the subscriber's `ack_policy` and refuses anything that is not `MANUAL`.
`consume_scope` reads it from `self.context.get("handler_")` — FastStream enters
that scope before any middleware — via `getattr(..., "ack_policy", None)`, so a
missing subscriber yields `None` and an undetermined policy is never judged.

The new branch sits **immediately after the batch refusal and before the
missing-handler check**: a batch subscriber is still the first thing reported,
but a non-MANUAL subscriber is misconfigured whether or not
`initialize_concurrent_processing` ever ran. `ACK_FIRST` never reaches the check
— it returns `_PassThrough` earlier on the `committed is not None` branch.

No restoration is needed: the parser builds a fresh message per record and it is
discarded once the task completes.

### The messages

Each names the method, says why it is unsafe *here*, and says what to do
instead. For `nack` the honest answer is that there is nothing to do:
**concurrent processing has no supported way to request redelivery**, since the
offset commits even when the handler raises. That message points at
[`decisions/2026-07-28-control-signals-not-honoured.md`](../decisions/2026-07-28-control-signals-not-honoured.md)
rather than suggesting a workaround that does not exist — as a **GitHub URL**,
not a repo-relative path, since a user who installed from PyPI has no checkout
to open it in.

## Non-goals

- **`msg.consumer.commit()` and `msg.consumer.seek()` stay unguarded.** The
  consumer is one shared `AIOKafkaConsumer` across every message and partition,
  so per-message shadowing does not apply, and wrapping it risks breaking the
  committer's own `commit(offsets)` calls. Reaching through the message to the
  raw consumer remains possible and remains dangerous; the README says so.
- No change to offset advance, the committer, or `_pending_state`.

## Testing

`uv run --no-sync pytest tests/test_middleware.py`

- Each of `ack` / `nack` / `reject` raises `RuntimeError` naming itself after a
  dispatch.
- The guard raises **without** `await`, pinning the synchronous choice — an
  async guard would pass every other test here and fail only this one.
- **The negative case that protects the framework:** on the FakeConsumer path
  and the auto-ack (`committed is not None`) path, the methods are untouched
  (`"ack" not in vars(msg)`). Guarding either would break `TestKafkaBroker` and
  the `ACK_FIRST` path respectively.
- `_classify` is unit-tested directly against **all five** ack policies, pinning
  the corrected table: `MANUAL` → `_Dispatch`, `ACK_FIRST` → `_PassThrough`,
  `ACK` / `REJECT_ON_ERROR` / `NACK_ON_ERROR` → `_Refuse`. Plus both new
  orderings: batch beats the policy refusal, the policy refusal beats the
  missing-handler one, and `ack_policy=None` refuses nothing.
- Guarding one message leaves another instance unaffected, pinning instance
  shadowing rather than class patching.
- `tests/test_integration.py` — real broker: a handler calling `await msg.ack()`
  fails that message, the consumer keeps running, and later messages still
  process and commit.

## Risk

This converts two currently-silent bugs into runtime errors. Anyone calling
`msg.ack()` today, or running a concurrent subscriber under `AckPolicy.ACK` /
`REJECT_ON_ERROR` / `NACK_ON_ERROR`, is already losing messages, so both are a
rescue rather than a regression — but both surface as new failures in code that
appeared to work. The ack-policy refusal is the louder of the two: it fires on
the *first* message of an affected subscriber, at startup rather than on a rare
path. The release notes must say so.

A handler wrapping its body in a broad `except Exception` will swallow the
guard's error. The ack is still prevented — the data loss cannot happen — but
the diagnostic is lost. Nothing can be done about that from this side.
