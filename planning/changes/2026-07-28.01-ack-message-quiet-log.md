# Change: Stop logging AckMessage as a task failure

**Lane:** lightweight — ≲30 LOC net, ≤2 files, no new file, no public-API
change, a single straightforward test.

## Goal

A middleware registered *after* `KafkaConcurrentProcessingMiddleware` runs
**inside** the coroutine we fire as a background task. When it raises
`AckMessage` — a FastStream control-flow signal, not a failure —
`_finish_task` logs it at ERROR with a full traceback, once per message.
Make that path quiet.

## Motivation

FastStream wraps `middlewares[::-1]` in registration order
(`_internal/endpoint/subscriber/usecase.py:380`), so a later-registered
middleware is inner: its `consume_scope` *is* the `call_next(msg)` coroutine
handed to `handle_task` (`processing.py:48`). An `AckMessage` raised there
never leaves the task, so `_finish_task` (`processing.py:33-39`) sees it as a
plain task exception and formats a traceback for it.

Measured, dispatching through the real handler and committer with a null log
sink, varying the depth of the frames below the middleware:

| | CPU/msg | log bytes/msg | throughput |
|---|---|---|---|
| normal handler | 139 µs | 0 | 5,743 msg/s |
| inner mw raises `AckMessage`, depth 12 | 342 µs | 1,221 | 2,488 msg/s |
| inner mw raises `AckMessage`, depth 40 | 750 µs | 1,222 | 1,273 msg/s |

Cost scales with stack depth, and real chains are deep. The handler never even
ran — this is pure traceback formatting on what the user intended as a cheap
per-message ack. Every record is also live until the log handler drains it.

The committer itself is **not** implicated: loop iterations are identical for
ack-raising and normal messages (2002 for 2000 messages) and zero while idle,
so there is no busy-loop to fix.

## Approach

In `_finish_task`, branch on `AckMessage` before the generic error log:

```python
if isinstance(exc, AckMessage):
    logger.debug("Kafka middleware. Task signalled AckMessage")
elif exc:
    logger.error("Kafka middleware. Task has failed with the exception", exc_info=exc)
```

`isinstance` handles `exc is None` on its own, so the existing `if exc` guard
moves to the `elif`. Offset handling is untouched: the task is done and not
cancelled, so its offset is committed exactly as today — which already matches
what `AckMessage` asks for. Under `AckPolicy.MANUAL` FastStream builds no
`AcknowledgementMiddleware` at all (`kafka/subscriber/config.py:44`), so
nothing else in the stack interprets the signal.

Every other exception, including the sibling `HandlerException`s
(`NackMessage`, `SkipMessage`, `RejectMessage`) and `StopConsume`, keeps the
ERROR-with-traceback log. Their semantics under concurrent processing are a
separate, larger question — parked in
[`deferred.md`](../deferred.md#control-flow-signals-other-than-ackmessage-inside-dispatched-tasks).
