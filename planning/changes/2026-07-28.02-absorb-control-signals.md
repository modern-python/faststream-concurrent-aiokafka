# Change: Absorb every control-flow signal at the dispatch boundary

**Lane:** full — cross-cutting behaviour change, non-trivial test design.

## Summary

[`2026-07-28.01`](2026-07-28.01-absorb-ack-message-at-dispatch.md) absorbed
`AckMessage` in `_absorb_ack_message`. This extends the shield to the whole
`IgnoredException` family, grouped into three ordered `except` branches by log
level. Every signal is absorbed; the level states whether the library actually
honored it.

## Motivation

A middleware registered *after* `KafkaConcurrentProcessingMiddleware` is
**inner** — FastStream wraps `middlewares[::-1]` in registration order — so its
`consume_scope` *is* the coroutine dispatched as a background task. Under
`AckPolicy.MANUAL` FastStream builds no `AcknowledgementMiddleware`
(`kafka/subscriber/config.py`), so nothing interprets these signals.

**`StopApplication` tears down the event loop.** It subclasses both `Exception`
and `SystemExit` (MRO: `StopApplication → IgnoredException → FastStreamException
→ Exception → SystemExit → BaseException`), and asyncio's `Task.__step`
special-cases `SystemExit`: it sets the task exception *and re-raises into the
event loop*. Measured:

```
StopConsume:
  task done=True cancelled=False exc=StopConsume()
  loop survived, main still running
StopApplication:
  asyncio.run() PROPAGATED StopApplication: loop torn down
```

The application dies abruptly: in-flight tasks abandoned, the committer's
bounded shutdown flush never runs, every in-flight offset lost. This corrects
the record — `deferred.md` claimed these signals meant "the app never exits",
which understated `StopApplication` as an inconvenience rather than a crash.

The remaining signals carry the two costs `2026-07-28.01` documented and fixed
for `AckMessage`: the task retains the exception, its traceback, and every frame
the traceback references — including the message body — until the offset
commits; and `sentry_sdk`'s `AsyncioIntegration` wraps every task coroutine in
`try: await coro / except Exception: reraise(*_capture_exception())`, reporting
each as an **unhandled** error. All six subclass `Exception`, so all six are
captured.

## Design

`processing.py`'s `_absorb_ack_message` becomes `_absorb_control_signal`, keeping
its single `try` and grouping the family into three ordered `except` branches by
log level:

```python
try:
    return await coroutine
except (AckMessage, RejectMessage, SkipMessage) as exc:
    logger.debug("Kafka middleware. Task signalled %s; the offset commits", type(exc).__name__)
except (NackMessage, StopConsume, StopApplication) as exc:
    logger.error("... %s, which concurrent processing cannot honour ...", type(exc).__name__)
except IgnoredException as exc:
    logger.error("... unrecognised FastStream control signal %s ...", type(exc).__name__)
return None
```

An earlier draft put this in a separate `_signals.py` as a policy table plus a
`classify_signal` lookup, on the grounds that the repo isolates decision logic
that way (`_pending_state.py`, `_commit_scheduler.py`, `_classify` in
`middleware.py`). That was over-engineering for three log levels: those modules
isolate real branching complexity, whereas this is a fixed six-way mapping onto
two levels. Grouped `except` branches let Python's own exception matching do the
dispatch — which handles user subclasses of a known signal for free, where a
dict keyed on `type(exc)` would not — and delete a module, a dataclass, and its
test file. The branch order is load-bearing in the same way `_classify`'s is:
both named groups must precede the `IgnoredException` catch-all.

The two ERROR branches use `logger.error`, not `logger.exception`, and carry
`# noqa: TRY400` saying so — a traceback here is precisely the noise being
removed.

`_finish_task` is untouched, including its close-on-cancel path. No public API
changes.

| raised inside the task | offset | log | honored? |
|---|---|---|---|
| `AckMessage` | commit | DEBUG | yes — committing *is* the ack |
| `RejectMessage` | commit | DEBUG | yes — for Kafka `reject()` is `ack()` |
| `SkipMessage` | commit | DEBUG | yes — skip and move on |
| `NackMessage` | commit | ERROR | no — asks for redelivery, we advance |
| `StopConsume` | commit | ERROR | no — subscriber keeps consuming |
| `StopApplication` | commit | ERROR | no — app keeps running |
| unknown `IgnoredException` | commit | ERROR | unknown — absorbed so a future signal cannot crash the loop |
| any other exception | commit | ERROR + traceback | unchanged; still ends the task |

Offset behavior is unchanged throughout. The committer commits a task that is
`done()` and not `cancelled()`; a task returning `None` is exactly that.

### The price of this design

Two gaps are accepted deliberately, and the ERROR log is the whole mitigation:

- **An app that asks to stop will not stop.** `StopApplication` and
  `StopConsume` become loud ERRORs and execution continues. Strictly safer than
  today's silent loop teardown, but an operator must act on the log.
- **`NackMessage` still commits**, contradicting its caller, exactly as today.

Honoring the stop signals was considered and rejected: it needs the subscriber
captured from the scoped `"handler_"` context at dispatch time
(`usecase.py:344` — the scope is gone by the time the task runs), a `weakref`
guard against concurrent stop requests, and a decision about offset advance with
no good answer — the only existing "do not advance" mechanism is the
cancelled-task watermark, which is cleared only on rebalance, so reusing it would
stop every later offset on that partition from committing until the group
rebalances. Honoring `NackMessage` was rejected earlier for the same reason.

## Non-goals

- Guarding direct `msg.ack()` / `msg.nack()` calls from an inner middleware.
  Stays in [`deferred.md`](../deferred.md) with its revisit trigger.
- Any change to offset advance, watermarks, or `_pending_state`.

## Testing

- `tests/test_concurrent_processing.py` — through the real dispatch path: each of
  the six signals leaves the task with `exception() is None` and `result() is
  None`, and logs at its group's level, with the signal named in the message. An
  unrecognised `IgnoredException` subclass hits the catch-all at ERROR. A real
  `ValueError` still ends the task, so the shield cannot silently widen.
- `tests/test_concurrent_processing.py` — **the crash regression**: dispatching a
  task that raises `StopApplication` leaves the event loop alive.
- `tests/test_integration.py` — real Redpanda: an inner middleware raising
  `StopApplication` on the *first* message only. The app survives and every later
  message still reaches the handler, so the test proves consumption continued
  past the signal rather than merely that the loop is alive.

A note for anyone reproducing the red state: `StopApplication` escaping into the
task does *not* abort the pytest session as first predicted. `CallInfo.from_call`
catches `BaseException`, so it surfaces as an ordinary failure whose traceback
terminates at the `raise` rather than at an assertion.

## Risk

Widening `except AckMessage` to `except IgnoredException` catches more than
before. `SkipMessage` is also raised by FastStream's own filter machinery, but
that runs in `is_suitable` *before* middlewares are entered
(`usecase.py:358-360`), so it cannot reach the shield. Any other
`IgnoredException` reaching the shield came from inside the dispatched
coroutine, which is exactly what the shield is for.

Absorbing an unknown future `IgnoredException` is deliberate: crashing the loop
is never the better default, and the ERROR names the unhandled signal.
