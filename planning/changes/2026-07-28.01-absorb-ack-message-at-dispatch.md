# Change: Absorb AckMessage at the dispatch boundary

**Lane:** full — the fix changes what the dispatched task *is*, not just how a
callback logs, and its correctness argument spans the committer's retention of
completed tasks and third-party asyncio task wrappers.

## Summary

`KafkaConcurrentHandler.handle_task` now wraps the user coroutine in
`_absorb_ack_message` before turning it into a task. An `AckMessage` raised by a
middleware registered *after* `KafkaConcurrentProcessingMiddleware` is caught
there and the task completes normally, instead of ending with an exception.

## Motivation

FastStream wraps `middlewares[::-1]` in registration order
(`_internal/endpoint/subscriber/usecase.py`), so a later-registered middleware is
**inner**: its `consume_scope` *is* the `call_next(msg)` coroutine that
`handle_task` fires as a background task. An `AckMessage` raised there never
leaves the task, and under `AckPolicy.MANUAL` FastStream builds no
`AcknowledgementMiddleware` at all (`kafka/subscriber/config.py`), so nothing
interprets it.

Two costs follow, and neither is a logging problem:

**Retention.** The task keeps the exception, its traceback, and every frame the
traceback references — including the message body — alive until the committer
commits the offset. Measured with a batch size high enough that nothing commits,
2000 messages each carrying an 8 KB body:

| | tasks still holding an exception | retained |
|---|---|---|
| exception ends the task | 2000 / 2000 | 39,385 B/msg |
| absorbed in the shield | 0 / 2000 | 18,539 B/msg |

The shield's figure is identical whether the payload is shared or per-message,
i.e. it frees the body. At the default `max_uncommitted_tasks=10_000` the
difference is roughly 200 MB of pinned bodies under a commit backlog.

**Error reporters.** `sentry_sdk`'s `AsyncioIntegration` installs a task factory
that wraps every task coroutine in
`try: await coro / except Exception: reraise(*_capture_exception())`, capturing
with `mechanism={"type": "asyncio", "handled": False}`. `AckMessage` subclasses
`Exception`, so it is reported as an **unhandled error** from inside the task no
matter what level we log at. This is what makes a log-level-only fix insufficient.

For reference, the traceback-formatting cost that a log-level fix does address:
139 µs/msg on the normal path versus 342 µs at call depth 12 and 750 µs at depth
40, plus ~1.2 KB of log output per message. After the shield, the ack path costs
147.7 µs/msg against a 140.3 µs baseline.

## Design

```python
async def _absorb_ack_message(coroutine: typing.Awaitable[typing.Any]) -> typing.Any:
    try:
        return await coroutine
    except AckMessage:
        logger.debug("Kafka middleware. Task signalled AckMessage")
        return None
```

`handle_task` dispatches `asyncio.ensure_future(_absorb_ack_message(coroutine))`.

Offset behavior is unchanged. The committer commits a task that is `done()` and
not `cancelled()`; a task that returns `None` and a task that ended with
`AckMessage` are both exactly that. Both measured runs above show `pending=2000`.

Only `AckMessage` is absorbed. Every other exception still ends the task and is
logged by `_finish_task` at ERROR with its traceback, unchanged.

**The wrapper introduces one hazard, which the design must handle.** `stop()`
cancels tracked tasks; if it cancels the shield *before its first step*, the
shield's body never runs and the coroutine it holds is never awaited. Previously
the task owned that coroutine directly and closed it on cancellation. So
`_finish_task` takes the coroutine as its first argument (bound via
`functools.partial`) and, on the cancelled path, closes it when it is still
`CORO_CREATED`. Without this, the dropped coroutine raises a `RuntimeWarning`
through `sys.unraisablehook` — into the same logs and error reporter this change
exists to keep quiet.

## Non-goals

- The sibling signals `NackMessage`, `SkipMessage`, `RejectMessage`,
  `StopConsume`, `StopApplication`. They keep ending the task and logging at
  ERROR. Parked in [`deferred.md`](../deferred.md) with revisit triggers.
- Guarding direct `msg.ack()` / `msg.nack()` calls. Also parked there.

## Testing

`uv run --no-sync pytest tests/test_concurrent_processing.py`

- `test_concurrent_ack_message_never_reaches_the_task` — the task ends with
  `exception() is None` and `result() is None`. This is the retention and
  error-reporter pin; it fails against the pre-change code with
  `assert AckMessage() is None`.
- `test_concurrent_real_exception_still_reaches_the_task` — a `ValueError` still
  ends the task, so the shield cannot silently widen.
- `test_concurrent_closes_user_coroutine_when_shield_cancelled_before_first_step`
  — after cancelling before the first step, the wrapped coroutine is
  `CORO_CLOSED`.
- `test_concurrent_failed_task_exception` — a genuine failure still logs ERROR
  *with* `exc_info`.

## Risk

The shield adds a coroutine frame per message. Measured at 140.3 µs/msg on the
normal path both with and without it — no detectable cost.

The cancelled-before-first-step path is the subtle one; it is covered by its own
test, and it was found by the suite emitting a `RuntimeWarning` rather than by
inspection. A pre-existing, unrelated `RuntimeWarning` in
`tests/test_kafka_committer.py` is present before and after this change and is
out of scope.
