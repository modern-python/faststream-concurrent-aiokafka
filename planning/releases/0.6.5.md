# faststream-concurrent-aiokafka 0.6.5 — non-MANUAL subscribers are finally left alone

**Patch release with one important bug fix and one new guard.** No API changes. **If you register this middleware at broker level across a mix of ack policies, read section 1 — those subscribers were being silently mishandled.**

Spec: [`planning/changes/2026-07-28.03-guard-direct-ack.md`](../changes/2026-07-28.03-guard-direct-ack.md).

## 1. Non-MANUAL subscribers were being dispatched, and double-acked

**If you have `AckPolicy.ACK`, `REJECT_ON_ERROR` or `NACK_ON_ERROR` subscribers under a broker-level registration of this middleware, they were losing messages. This release fixes that.**

### The gap

The library is meant to be registered once at broker level across a mix of subscribers: `AckPolicy.MANUAL` ones become concurrent, everything else behaves as if the middleware were not registered. That is what `CLAUDE.md` and the README have always documented. The implementation never delivered it.

`_classify` decided "is FastStream managing acks here?" by asking a proxy question — *does this message arrive already marked acked?* That catches `ACK_FIRST`, whose messages start `ACKED`. It says nothing about the policies where FastStream acks **later**: `faststream/kafka/subscriber/usecase.py` builds `KafkaMessage` only when `ack_first`, so `ACK`, `REJECT_ON_ERROR` and `NACK_ON_ERROR` all arrive with `committed=None` — indistinguishable from `MANUAL`.

So those subscribers were **dispatched concurrently**. And because `faststream/kafka/subscriber/config.py` disables auto-ack only for `MANUAL`/`ACK_FIRST`, FastStream *also* built its own `AcknowledgementMiddleware` for them. The result, on every message:

1. Our `consume_scope` fired the handler as a background task and returned immediately.
2. The chain unwound; `AcknowledgementMiddleware.__aexit__` saw no exception and called `message.ack()`.
3. That issues a bare `consumer.commit()` with no offsets, which aiokafka documents as committing the *current consumed offsets* for the consumer's partitions.
4. Because step 1 returns instantly, the consume loop had already raced ahead. The committed position was past work still running.

Crash, redeploy or rebalance at that point and those in-flight messages were gone: marked processed, never redelivered, never handled. Silently, with no exception and nothing in metrics.

### The fix

`_classify` now takes the subscriber's real `ack_policy`, read from the `"handler_"` context scope, and **passes through anything that is not `MANUAL`** — the documented behaviour. The branch sits before the batch check, so a `batch=True` subscriber on a non-MANUAL policy also passes through cleanly rather than being rejected; it is none of this library's business.

Pass-through is safe because each FastStream subscriber builds its **own** `AIOKafkaConsumer`, so its ack touches only its own partitions, and with no background task "consumed" and "processed" stay the same moment, exactly as in stock FastStream. The hazard existed only because those subscribers were being dispatched.

| policy | `batch=False` | `batch=True` |
|---|---|---|
| `MANUAL` | dispatch (concurrent) | refuse — batch is unsupported |
| `ACK_FIRST` | pass through | pass through |
| `ACK` | pass through | pass through |
| `REJECT_ON_ERROR` | pass through | pass through |
| `NACK_ON_ERROR` | pass through | pass through |

## 2. Direct `msg.ack()` / `nack()` / `reject()` now raise

**One-line impact: reaching around the batch committer is refused instead of silently losing data.**

### The gap

Offsets on the concurrent path belong to `KafkaBatchCommitter`. Nothing stopped a handler or middleware from bypassing it. `KafkaAckableMessage.ack()` issues the same bare `consumer.commit()` described above, committing past every in-flight task. `reject()` is `await self.ack()` for Kafka — the same hazard under an opposite-sounding name. `nack()` issues `consumer.seek()`, rewinding a partition underneath tasks already processing it.

### The fix

On the dispatch route only, all three methods are shadowed on the message instance with **synchronous** functions that raise an actionable `RuntimeError` naming the method. Synchronous is deliberate: the guard fires while `msg.ack()` is being *evaluated*, so a caller who forgets to `await` still gets an error rather than an un-awaited-coroutine warning. Passed-through subscribers never receive the guards.

There remains no supported way to request redelivery under concurrent processing — the offset commits even when your handler raises. See [`planning/decisions/2026-07-28-control-signals-not-honoured.md`](../decisions/2026-07-28-control-signals-not-honoured.md).

**Still unguarded:** reaching through the message to the raw consumer, as in `msg.consumer.commit()` or `msg.consumer.seek(...)`. One shared consumer serves every message on that subscriber, so it cannot be guarded per message. Do not do it.

## Upgrade notes

**Section 1 is a behaviour fix, not a break.** Non-MANUAL subscribers stop being wrongly dispatched and start behaving as documented. If you relied on `AckPolicy.ACK` subscribers running concurrently, they never safely did — they were losing messages. Declare `ack_policy=AckPolicy.MANUAL` to opt a subscriber into concurrency.

**Section 2 can surface as new errors.** A handler or middleware calling `msg.ack()`, `msg.nack()` or `msg.reject()` under a MANUAL subscriber now raises `RuntimeError` where it previously appeared to work. It did not work: it was committing offsets past in-flight tasks. Remove the call and let the committer manage offsets.
