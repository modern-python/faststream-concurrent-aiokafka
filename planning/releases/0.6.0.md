# faststream-concurrent-aiokafka 0.6.0 — robustness audit: rebalance-flush timeout, batch guard, backpressure

**Minor release. Three behavioral fixes from a code/docs/test audit, one new opt-out backpressure knob, plus packaging and docs.** No breaking API changes — every new parameter is additive with a behavior-preserving default. Two previously-unbounded failure paths (a rebalance hang and unbounded memory growth) are now bounded by default; see *Upgrade notes*.

Audit spec: [`planning/changes/archive/2026-06-13.01-robustness-docs-test-audit/design.md`](../changes/archive/2026-06-13.01-robustness-docs-test-audit/design.md).

## 1. Rebalance flush is now bounded (`flush_timeout_sec`)

**Fixes a potential consumer-group stall during rebalance.** `commit_all()` gains a `flush_timeout_sec` parameter (default `10.0`), plumbed through `KafkaConcurrentHandler.create_rebalance_listener(flush_timeout_sec=...)` → `ConsumerRebalanceListener`.

### The gap

`ConsumerRebalanceListener.on_partitions_revoked` calls `committer.commit_all()` to flush completed offsets before a partition is reassigned. `commit_all()` did `self._flush_batch_event.set()` then `await self._messages_queue.join()` — and `join()` only returns once `task_done()` has fired for *every* enqueued task, which happens only when a task completes **and** is committed. So the revoke callback blocked until every in-flight handler — across *all* partitions, not just the revoked ones — finished, with **no timeout**.

aiokafka awaits `on_partitions_revoked` inside the consumer's group-coordination path, against the broker's rebalance clock. A single slow or hung handler could overrun `max.poll.interval.ms`, get the member evicted, and trigger a cascading rebalance storm.

### The fix

`commit_all()` now wraps the join in `asyncio.wait_for(..., timeout=flush_timeout_sec)`. On `TimeoutError` it logs a warning and returns: offsets for already-completed tasks are committed, and anything still in-flight stays uncommitted and is redelivered after reassignment (at-least-once — duplicates only on the timeout path). Cancelling the inner `join()` does not disturb the queue's unfinished-task counter, and the committer keeps running and flushing afterward. The default `10.0` s sits comfortably under aiokafka's default `max.poll.interval.ms` (300 s).

Scoping the wait to *only* the revoked partitions (rather than a bounded global wait) remains a documented future optimization.

## 2. Batch subscribers are rejected with a clear error

**One new guard; turns an opaque crash into an actionable message.** No effect on non-batch subscribers.

### The gap

On the MANUAL-ack concurrent path, `consume_scope` casts the raw message to a single `ConsumerRecord` and reads `record.offset / topic / partition`. With `@broker.subscriber(batch=True, ack_policy=AckPolicy.MANUAL)`, the raw message is a *tuple* of records, so this raised a bare `AttributeError` deep in the dispatch path — confusing, and with no hint that batch mode is unsupported.

### The fix

`consume_scope` now detects a batch raw message (`isinstance(self.msg, (list, tuple))`) and raises a clear `RuntimeError` explaining that batch subscribers are not supported and how to proceed. The check sits **after** the FakeConsumer (`TestKafkaBroker`) and non-MANUAL pass-throughs, so those paths are untouched — it fires only where the crash used to happen. Supporting batch mode remains out of scope.

## 3. Opt-in backpressure on uncommitted tasks (`max_uncommitted_tasks`)

**New parameter on `initialize_concurrent_processing` (default `10000`, `None` disables).** Bounds memory during a commit/broker outage.

### The gap

The internal commit queue had no bound, and a transient `KafkaError` re-queues the failed batch for retry. The concurrency semaphore caps only *in-flight* tasks — completed-but-uncommitted tasks accumulate in per-partition pending state (and re-queued failures bounce through the queue) without limit while the broker rejects commits. A sustained outage grew memory until OOM; nothing linked commit lag back to consumption.

### The fix

`KafkaBatchCommitter` now tracks an uncommitted-task count (admitted via `send_task`, released once committed or dropped) and, when it reaches `max_uncommitted_tasks`, `send_task` blocks. That stalls the consume path so the consumer stops fetching until commits catch up — backpressure propagates through the existing semaphore and poll loop. Hitting the ceiling also nudges the committer to flush, so a backpressured producer isn't left waiting for the batch timeout. The block stays responsive to shutdown (a dead committer surfaces as `CommitterIsDeadError` rather than hanging). Set `max_uncommitted_tasks=None` to restore the previous unbounded behavior.

Each uncommitted entry holds only commit metadata — a task reference, its `TopicPartition`, offset, and consumer reference — not the message payload, so the `10000` default is on the order of a few MB. Keep it `>= commit_batch_size` so size-based batching can still trigger.

## Upgrade notes

Drop-in for existing code — no API changed shape. Two defaults now bound previously-unbounded paths:

- **Rebalance flush** is capped at `flush_timeout_sec=10.0` s (was unbounded). If your handlers can legitimately run longer than 10 s and you rely on the rebalance flush awaiting them, raise it via `handler.create_rebalance_listener(flush_timeout_sec=...)`.
- **Backpressure** defaults to `max_uncommitted_tasks=10000`. Under a sustained commit/broker outage the consume path will now stall instead of growing memory without bound. Pass `max_uncommitted_tasks=None` to `initialize_concurrent_processing` to restore the old unbounded behavior.
- **Batch + MANUAL subscribers** now raise a clear `RuntimeError` at dispatch. This configuration never actually worked (it crashed with an `AttributeError`); the error now names the cause.
