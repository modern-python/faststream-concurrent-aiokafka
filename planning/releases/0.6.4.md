# faststream-concurrent-aiokafka 0.6.4 — StopApplication no longer kills the application

**Patch release. The dispatch shield now absorbs every FastStream control signal, not just `AckMessage`.** No breaking API changes, no changed defaults, no change to offset semantics.

Spec: [`planning/changes/2026-07-28.02-absorb-control-signals.md`](../changes/2026-07-28.02-absorb-control-signals.md).

## 1. Every control signal is absorbed at the dispatch boundary

**If a middleware registered after `KafkaConcurrentProcessingMiddleware` raises `StopApplication`, your application no longer dies.**

### The gap

A middleware registered *after* `KafkaConcurrentProcessingMiddleware` is **inner** — FastStream wraps `middlewares[::-1]` in registration order — so its `consume_scope` *is* the coroutine this library dispatches as a background task. [0.6.3](0.6.3.md) absorbed `AckMessage` there. The rest of the family still ended the task, and one of them was far worse than noise:

`StopApplication` subclasses **both** `Exception` and `SystemExit`, and asyncio's `Task.__step` special-cases `SystemExit`: it sets the task exception *and re-raises it into the event loop*. Measured before the fix:

```
StopConsume:
  task done=True cancelled=False exc=StopConsume()
  loop survived, main still running
StopApplication:
  asyncio.run() PROPAGATED StopApplication: loop torn down
```

The application died abruptly — in-flight tasks abandoned, the committer's bounded shutdown flush skipped, every in-flight offset lost. `NackMessage`, `SkipMessage`, `RejectMessage` and `StopConsume` each carried the costs 0.6.3 documented for `AckMessage`: a retained traceback pinning the message body until the offset committed, and an **unhandled** error report from asyncio-aware reporters such as `sentry_sdk`'s `AsyncioIntegration`.

### The fix

`_absorb_control_signal` groups the family into three ordered `except` branches. Every signal is absorbed and its offset commits; the log level says whether the library could honour it, and the signal is named in the message.

| signal | log | honoured? |
|---|---|---|
| `AckMessage` | DEBUG | yes — committing *is* the ack |
| `RejectMessage` | DEBUG | yes — for Kafka `reject()` is `ack()` |
| `SkipMessage` | DEBUG | yes — skip and move on |
| `NackMessage` | ERROR | no — asks for redelivery, we advance |
| `StopConsume` | ERROR | no — the subscriber keeps consuming |
| `StopApplication` | ERROR | no — the application keeps running |
| unrecognised `IgnoredException` | ERROR | unknown — absorbed so a future signal cannot crash the loop |

Every exception outside the family still ends the task and logs at ERROR with its traceback, unchanged.

## Upgrade notes

Drop-in. No API, defaults, or offset semantics changed.

**Know this if you rely on these signals.** `NackMessage`, `StopConsume` and `StopApplication` are absorbed but **not honoured**: a nacked message is still committed rather than redelivered, a subscriber asked to stop keeps consuming, and an application asked to exit keeps running. Each now logs a loud ERROR naming the signal. That is strictly safer than the previous behaviour — a silent loop teardown losing in-flight offsets — but if your code depends on any of them taking effect from inside a concurrently dispatched handler, it never did, and now you get told. Honouring them is tracked in [`planning/deferred.md`](../deferred.md).
