# faststream-concurrent-aiokafka 0.6.3 — AckMessage no longer ends the dispatched task

**Patch release. An `AckMessage` raised by a middleware registered after `KafkaConcurrentProcessingMiddleware` is now absorbed inside the dispatched coroutine instead of ending the asyncio task.** No breaking API changes, no changed defaults. Offset semantics are unchanged.

Spec: [`planning/changes/2026-07-28.01-absorb-ack-message-at-dispatch.md`](../changes/2026-07-28.01-absorb-ack-message-at-dispatch.md).

## 1. AckMessage is absorbed at the dispatch boundary (`_absorb_ack_message`)

**If you raise `AckMessage` from a middleware registered after ours, it no longer pins message bodies in memory and no longer shows up in your error reporter.**

### The gap

FastStream wraps subscriber middlewares as `middlewares[::-1]` in registration order, so a middleware registered *after* `KafkaConcurrentProcessingMiddleware` is **inner**: its `consume_scope` *is* the coroutine this library fires as a background task. An `AckMessage` raised there never leaves that task, and under `AckPolicy.MANUAL` FastStream builds no `AcknowledgementMiddleware` at all, so nothing interprets it. The task therefore ended with an exception, which cost two things:

- **Retained memory.** The task kept the exception, its traceback, and every frame the traceback references — including the message body — alive until the committer committed the offset. Measured under a commit backlog with an 8 KB body: **39,385 B/message retained**. At the default `max_uncommitted_tasks=10_000` that is roughly 200 MB of pinned bodies.
- **Spurious error reports.** `sentry_sdk`'s `AsyncioIntegration` installs a task factory that wraps every task coroutine in `try: await coro / except Exception: reraise(*_capture_exception())` and captures with `mechanism={"type": "asyncio", "handled": False}`. `AckMessage` subclasses `Exception`, so every ack was reported as an **unhandled error**, regardless of log level.

### The fix

`handle_task` wraps the user coroutine in `_absorb_ack_message` before creating the task. `AckMessage` is caught there, logged at DEBUG without a traceback, and the task completes normally with `None`. Retention drops to **18,539 B/message**, identical to a message carrying no exception at all, and no task-factory wrapper ever sees the signal.

Offset behavior is unchanged: the committer commits a task that is `done()` and not `cancelled()`, which a normally-completing task also is. Any `extra_options` passed to `AckMessage(**extra_options)` are ignored, as they were before — the ack here is a batched offset commit, not a per-message `message.ack(**extra_options)` call.

Only `AckMessage` is absorbed. Every other exception still ends the task and is logged at ERROR with its traceback, unchanged. The sibling signals `NackMessage`, `SkipMessage`, `RejectMessage`, `StopConsume` and `StopApplication` are **not** handled — see [`planning/deferred.md`](../deferred.md).

- New: the task ends with no exception on `AckMessage`; a real `ValueError` still ends the task; a shield cancelled before its first step still closes the coroutine it wraps.

## Upgrade notes

Drop-in. No API, defaults, or offset semantics changed.

One observable difference if you were relying on it: an `AckMessage` from an inner middleware previously surfaced as an ERROR log with a traceback and as an unhandled event in error reporters. It is now a DEBUG log and nothing else. If you had alerting keyed on those events, it will go quiet — that is the point of the release.

## Release process

Tag-driven (`.github/workflows/release.yml`): pushing a bare semver tag (no `v` prefix) to `main` publishes to PyPI via Trusted Publishing and creates the matching GitHub Release. Curated notes at `planning/releases/<tag>.md` are mandatory for a stable tag and must exist at the tagged commit; the workflow fails before publishing if they are missing.
