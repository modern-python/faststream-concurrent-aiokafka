## 1. Cancellation-watermark clearing now covers every consumer on a revoked partition

**Corrects the rebalance watermark-clear for processes that run more than one consumer over the same `(topic, partition)` (e.g. a `KafkaRouter` with multiple subscribers sharing one handler).** A latent correctness fix — see the scope note below.

### The gap

Cancellation watermarks (the "do not advance past this cancelled offset" floors that preserve at-least-once on an abrupt stop) are keyed per `(consumer-id, TopicPartition)` precisely so a cancelled task on one consumer can't block commits on another consumer that happens to subscribe to the same partition. But the rebalance clear, `clear_cancellation_watermarks(partitions)`, resolved a single owner per partition through a `_partition_owner` map (the *most recent* consumer to absorb a task there) and cleared only that one consumer's floor. If a second consumer also held a floor for the revoked partition, it was left stuck — that consumer could stay blocked from advancing past the cleared partition's offsets on its next assignment.

### The fix

The `_partition_owner` indirection is removed. Clearing is now scoped by partition directly: `clear_watermarks(partitions)` drops **every** `(consumer-id, partition)` floor whose partition is being revoked. The behaviour is identical for the common single-consumer case and strictly more correct when two consumers share a partition. A regression test (`test_clear_watermarks_clears_every_consumer_on_partition`) pins it.

**Scope.** This is a defensive/latent fix: in the current code a cancellation watermark is only ever written during `handler.stop()` (the sole path that cancels user tasks), when every consumer sharing the handler is being torn down together — so the stuck-floor scenario is hard to reach in practice today. The fix makes the clear semantics obviously correct and forward-safe if a non-shutdown cancellation path is ever added (a code comment marks that contract).

## Internal

Three deepening refactors, each strictly behaviour-preserving (verified by the integration/middleware/rebalance suites passing untouched across Python 3.11–3.14 on real Redpanda) and each promoted into the affected `architecture/` doc:

- **`PendingCommits`** (`_pending_state.py`) — the committer's per-partition pending lists, pending count, and cancellation watermarks now live behind a small synchronous interface; `batch_committer.py` keeps the queue, backpressure, commit I/O, and re-queue. (Also carries the §1 watermark fix.)
- **`CommitScheduler`** (`_commit_scheduler.py`) — the streaming loop's *when-to-commit* decision state (timeout deadline, flush/shutdown lifecycle, batch trigger) is now a pure synchronous decider; `_run_commit_process` stays the async driver and writes no decision flag. Together with `PendingCommits` this splits `batch_committer.py` into "what to commit" and "when".
- **`_classify`** (`middleware.py`) — `consume_scope`'s 8-branch message-routing decision is now a pure `_classify(...) -> _Route` (`_PassThrough | _Dispatch | _Skip | _Refuse`); `consume_scope` is a precondition + an exhaustiveness-checked `match`. The decision is unit-testable with no broker/context/consumer plumbing.

No public-API or behaviour change from any of the three — `KafkaBatchCommitter`, `KafkaConcurrentHandler`, the middleware, and the lifecycle functions keep their existing surface.

## Upgrade notes

Drop-in. No API changed shape; every refactor preserves behaviour.

- **Multi-consumer watermark clearing (§1)** is the only behavioural change, and only in the niche case of two consumers covering the same `(topic, partition)` in one process during a rebalance: such a partition's cancellation floors are now *all* cleared on revoke, rather than only the most-recent owner's. Single-consumer deployments are unaffected. There is nothing to configure.
